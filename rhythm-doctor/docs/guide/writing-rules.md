# 文档规范

## 基本原则

- 使用中文说明。
- 不使用图形表情符号。
- 不使用偏紫配色或原子化样式框架。
- 只写已经从源码、调用点、Unity 配置或反编译结果中确认过的内容。
- 大页面必须拆分，优先通过侧边栏和交叉链接组织内容。

## 源码解释规则

- 不把猜测写进正式页面。
- 读不懂的成员继续追调用点、父类、子类、Unity 资源引用和反编译结果。
- 当轮没有查清的成员先不写解释，只保留在工作清单里。
- 对反编译命名明显不自然的地方，可以说明“名称来自当前源码导出结果”，但正文仍以实际代码行为为准。

## 类页面结构

每个重点类页面应包含：

| 区块 | 内容 |
| --- | --- |
| 基本信息 | 源码路径、命名空间、继承关系、主要职责 |
| 用途概览 | 这个类在系统中的位置 |
| 字段表 | 名称、类型、可见性、初始化方式、作用 |
| 属性表 | 名称、类型、读写能力、依赖对象、作用 |
| 方法表 | 签名、参数、返回值、主要行为、调用关系 |
| 生命周期 | Unity 生命周期方法、初始化顺序、运行时调用路径 |
| 相关类型 | 父类、子类、协作类、事件或数据模型 |
| 注意事项 | 反编译命名、外部调用风险、调用前提 |

## 模块页面结构

每个模块页面应包含：

- 模块边界。
- 主要职责。
- 核心流程。
- 关键类型。
- 源码研究关注点。
- 缺失清单。

## API 草稿规则

API 草稿页可以由脚本生成，但不能直接等同于最终文档。核心模块必须人工复核：

- 保留源码路径。
- 保留类型签名和成员签名。
- 标明是否已经人工复核。
- 字段和方法解释必须尽量对应实际调用点。
